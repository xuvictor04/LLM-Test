### BLOCKING P4 — two readings produce different code

**Q-MEM-9 — does `maintain`'s probe call `read`?** BLOCKING. P4 writes `maintain`'s body in this phase. Reading (a) writes `read(mem, store, queries=…, promote=True)` and inherits `read`'s `n_reads`/`n_promoted`/`n_wrong_*` counters; reading (b) writes a second kNN with its own filtering and its own counters. The two produce different code, different counter semantics and different behaviour under `wrong_read`. The answer is forced by the parameter lists, but P4 must be *told*, because K6 cannot see an in-package call and no check will catch the wrong choice.

**Q-WORLD-8 — `soft_cull`'s irreversibility.** BLOCKING P4 (world). `grow()`'s cap test *is* the body P4 writes. "Count live and append" and "count live and reuse a dead slot" are different code with different buffer behaviour, different checkpoint geometry and different `blocked_reason` values — and the first one crashes in `update_fitness` once `n() > nmax`. P4 cannot write the obvious thing here because the obvious thing (the contract's own literal recommendation) is the one that breaks.

**Q-MEM-11 — undeclared census record types.** BLOCKING P4, cheaply. P4's first act in `memory/` and `domains/` is to define the record types; if the fields are not declared, P4 invents names, and the four `produces` entries that cross those boundaries become fabricated provenance that K11 (a name-appearance check, `tests/test_contract.py:1975-1980`) cannot detect. Two readings — producer's spellings vs consumer's spellings — give different field names at four call sites. One docstring edit unblocks it.

### NOT BLOCKING P4

**Q-MEM-4 — `pressure()` cannot reach `pressure_thresh`.** NOT BLOCKING. P4 writes `census` returning `pressure = main/(main+prob)` either way; the three-state Gate is a P5 artefact (`PLAN.md:182`). **One adjacent item does block, though, and should ride with it:** whether `probation_frac` (and hence the eviction branch, and hence `pressure`'s denominator) is measured **per owner block** or **over the store**. Nothing declares it; the two readings are different code in `write`'s eviction path, and the numbers differ by a factor of 64 in granularity.

**Q-MEM-8 — which pass `MEM.judge` rides.** NOT BLOCKING P4. `judge` is deferred, has no row, and its body is identical whichever pass calls it. It blocks the **P5 row** that reinstates it. One P4-visible sub-decision does bite: whether the checked set is incremental (stale `selfcon` only) or the whole store — that changes both the body and the cost by ~20×, and I recommend it be settled in the same ruling.

**Q-MEM-10 — `blend` returns probabilities.** NOT BLOCKING P4 (MEM's bodies are unaffected; `blend` keeps its signature under my recommendation). It **blocks P5** entirely: the `-0.097 → +0.085` b/B retrieval path has rows and no consumer until it is ruled on. **It must nevertheless be decided now, not in P5**, because option (c) moves four frozen EVAL signatures — `curve_probe`, `holdout_probe`, `generate`, `coherence` — and 116 of 121 entry points are still stubs. Cheap today, expensive after P5 writes against them.

**Q-WORLD-6 — WORLD's cadence wire.** NOT BLOCKING anything. `WORLD.manage` is deferred for three unrelated reasons (`plateau`, `add_param_group`/Q-OPT-7, `latent` backwards), so no row calls it and no wire could deliver a value to a body that does not run. It is a ledger-hygiene question with a budget consequence (23 of 25 couplings declared), not a code question.
